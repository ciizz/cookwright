## 1. Context

The charter's Secrets decision: never a plaintext env file, not even as a fallback; a secret is injected into one child process with target proof; three backends at launch (1Password `op`, macOS Keychain, `age` with a passphrase-protected identity as the free universal path); no backend configured means Level 2 is off. The origin repo proved the contract over three bundles after two incidents (a stale export aimed a dev run at production; a process listing printed a password into a transcript). Stage 5 lifts the mechanism into the package: one command, proofs as data and pure functions, backends behind one interface.

What exists (*measured* in this planning session, 2026-10-27):

- The config is at version 3; `KNOWN_KEYS.top` in `src/lib/config.mjs` refuses unknown keys, so `secrets` needs version 4. `ci` is the model for an optional object with no default. The loader imports the pack registry (`KNOWN_PACKS`, `PACKS`) and already validates `packs[].rules` against each manifest, so it can validate a proof kind the same way. Migrations are pure steps in `src/lib/migrations.mjs` (imports nothing; `addPacks` returns `packsKept` when the key is present); outcome texts in `messages.migrate.outcomes`. `config.test.mjs` ties the schema's property names to `KNOWN_KEYS.*` and `version.enum` to `[CONFIG_VERSION, …MIGRATIONS keys]`; `src/migrate.test.mjs` holds thirteen literal `version 3` assertions and `scripts/ci/fixture.sh` two (`c.version === 3`, `already at version 3`). An older-version config loads "migrated in memory" and doctor reads it as weak.
- `LEVELS` in `src/lib/levels.mjs` holds only level 0 (15 required rows, `repo.node_modules` among them); `secrets.env` is not required by it. Level 2 exists only in docs. Kickoff decision 1 keeps it that way: the `secrets.*` rows are orthogonal, like pack rows.
- Doctor's rows are the static table `CHECKS` in `src/lib/doctor/registry.mjs` (19 rows, `packs` last) plus per-pack rows; a check is synchronous, `(repo, probes) → { status, note }`; a throw is a FAIL line, a `TimedOut` a SKIP; `runOne` SKIPs on the `config`/`git` flags only. One shared 1800 ms budget (`withBudget`, `runBounded` = `spawnSync` in `src/lib/budget.mjs`), 1500 ms per call; a required row that runs after a slow row can find the budget spent. `doctor.test.mjs` derives counts from `Object.keys(CHECKS).length` and fakes tools through `probes({ hasTool, … })`. `repo.root` (the config root) can sit below `repo.top` (the work tree's top); `git show HEAD:<path>` and `ls-files` resolve from the top.

- The managed block: `RULES_VERSION = 3` in `src/lib/rules/block.mjs`; the marker carries the version; any byte change of the render reads `stale`. A bump touches `block.test.mjs`, `test-helpers.mjs` (`v2Block`/`v1Block` derive from a v3 render), `init.test.mjs`, `doctor.test.mjs` (`refreshed(3)`, stale cases) and this repo's `AGENTS.md` (`rules.block` FAILs until `init` reruns). The `setup` doc-sync rule fires on `agents-block.md`, `skills/setup/SKILL.md`, `packs/**` and `src/lib/packs/*`, met by any staged `docs/guides/*.md`; the playbook reserves `COOKWRIGHT_SKIP=doc-sync` for a commit with no doc implication.
- The setup skill is a table per doctor row; `skills.test.mjs` requires every `CHECKS` key in it, ties quoted note fragments to the real messages, and requires every `| PASS |` row's note to reappear under `## At the end`. The pack manifest has no key whitelist: `proofs`, `ambient` and `control` are accepted as data (they must not look like a rule).
- The fixture skips through `need <tool>` (prints `skipped`, `exit 0` for the whole script) unless `FIXTURE_STRICT=1`, which CI sets; `isolate_git` sets git variables only, not `HOME` or the environment; its one `doctor()` run asserts exact counts; CI installs gitleaks from a sha256-pinned release (one top-level binary) on the ubuntu fixture job and runs the fixture on every push to `bundle/**`; the macOS jobs run only `npm test`. This machine exports `SUPABASE_DB_URL` from `~/.zshrc` (a name only; the supabase pack's ambient list).
- On this machine: `op` 2.39.0, `age` 1.3.2, `age-keygen`, `security`, `gitleaks`, `supabase` on PATH; macOS 26.6.2; Node 20.19.4.
- `age --help`: "Passphrase encrypted age files can be used as identity files", so one `age -d -i <identity.age> <file.age>` decrypts both, age prompting for the passphrase on the tty it opens itself; cookwright never handles a passphrase. `age -p` with an empty passphrase generates one and prints it to stderr. `age-keygen` writes the key to stdout; `-R <file>` reads recipients (blank and `#` lines ignored); `-a` writes PEM armor (first line `-----BEGIN AGE ENCRYPTED FILE-----`; binary ciphertext starts `age-encryption.org/v1`). gitleaks' default ruleset has an `age-secret-key` rule, so an identity inside a repo is caught by the pre-commit scan; an `age1…` recipient and ciphertext are not matched. age ciphertext carries no sender authentication: anyone holding the public recipients file can write a valid ciphertext. age's release tarball holds `age/age` and `age/age-keygen`.
- `op inject`: template from stdin or `-i <file>`, resolved text to stdout; bare `op://vault/item/[section/]field` references are resolved, and `$VAR` inside a reference is expanded from the environment. The origin never used `op inject`, so it is measured by hand in this stage (kickoff scope 7). The origin measured that `op run -- psql "$VAR"` expands in the parent shell before injection; the same holds for `run`. `op` itself reads `OP_SERVICE_ACCOUNT_TOKEN`, `OP_CONNECT_HOST`, `OP_CONNECT_TOKEN` and `OP_SESSION_<account>` from the environment.
- `security add-generic-password`: "Use of the -p or -w options is insecure. Specify -w as the last option to be prompted." Measured by the plan-review's red team on this machine: `/usr/bin/security` prompts through `getpass(3)`, whose buffer is `_PASSWORD_LEN` (128) characters, the rest discarded without an error, and both the prompt and its retype truncate alike; `find-generic-password -w` prints a non-ASCII value as hex. `security -i` reads commands from stdin (its quoting and limits unmeasured). `find-generic-password -s -a` prints attributes; the origin's canary reads without `-w`. `create-keychain`, `unlock-keychain`, `set-keychain-settings`, `delete-keychain` give a throwaway keychain for tests.
- libpq connection URIs: the query string may carry `host`, `hostaddr`, `user`, `port`, `dbname`, `service`, `options`, `password`, `passfile`, and those override the authority part; the origin's `splitDbPassword` refuses the credential-bearing ones (names percent-decoded). The origin's anchored proof: project URL host `<ref>.supabase.co`; database URL username `<role>.<ref>` on the pooler or host `db.<ref>.supabase.co` direct; userinfo split at the *last* `@`; a ref in the password, path, query or database name is a mismatch; its read-only variant requires a `*pooler*` host for the username anchor. Its recipients-file guard: tracked, byte-identical to HEAD, fingerprints printed. Its redaction is a whole-URL `sed` over a pipe; its stated residual: the injecting process's environment block holds the values for the run.

## 2. Decisions

Taken by the developer on 2026-10-26 (kickoff): secrets sit beside the levels (the `secrets.*` rows are orthogonal; Level 2's requirement list claims them when Level 2 opens); the `age` ciphertext and recipients are tracked, the identity alone is the secret; a target without a proof is WARN in doctor and `unproved` on the banner.

Dispositions by the Judgment rules, recorded with `bundle decide` at kickoff:

1. Rule 3 (claim what was measured): `run` splits its argv at the first `--` before `parseArgv`; everything after it is the child's, verbatim, flags included. No `--`, or nothing after it, is the usage, exit 2. A target name is `^[a-z][a-z0-9-]*$`, a secret name `^[A-Z][A-Z0-9_]*$`, both validated by the config.
2. Rule 3 and rule 7: a proof names the names it covers, never infers them by value shape (a Sentry DSN beside a Supabase URL is a declared name with no proof, and the banner says so). `{ kind: 'supabase', ref, names? }` defaults `names` to those of `SUPABASE_URL` and `DB_URL` the target declares (invalid when neither); `{ kind: 'host', host, names }` requires `names`. Each covered name must be in the target's `names`; a covered value that does not satisfy the kind is a mismatch, never skipped; a proof covering zero names is invalid.
3. Rule 2 (a chosen state is WARN): a target without `proof` is `secrets.targets` WARN naming it and `unproved` on the banner; a declared proof that fails refuses the run with the kind's reason (the name, the expected identifier, the anchor that failed; a found ref only when the value parsed as a `*.supabase.co` URL, else `not a supabase.co URL`; never a value, host or password).
4. Rule 1 governs hooks; `run` is the user's own command and refusing is the product: a missing backend tool, a wrong platform, a missing name, a literal in a template, a failed proof, a malformed resolved line, a value on the child's command line (dispositions 21, 22) each print one line naming the fix, exit 125 (disposition 47), nothing spawned. The hooks are unchanged.
5. Rule 3: the redaction guarantee costs the child its output terminal, said rather than weakened. The child gets stdin inherited (a prompt that reads the terminal still works; `age` and `security` open the tty themselves), stdout and stderr as pipes through the redactor, so it sees no TTY on its outputs: no colour unless forced, no pager. The banner says so once. Redacted: every injected value, its `encodeURIComponent` form, and, for a value that parses as a URL with a password of at least 8 characters, that password alone, decoded and encoded, each replaced by `<NAME>`. The guide says these are the forms covered (a base64, JSON-escaped or shell-quoted value is not).
6. Rule 5 and rule 7: `secrets/` is a fixed directory at the config root (`secrets/<target>.env.tpl`, `secrets/<target>.env.age`, `secrets/recipients.txt`); the ciphertext is armored (`age -a`): text, diffable, through the pre-commit scan like any file (the fixture commits one). The identity lives at `$XDG_CONFIG_HOME/cookwright/identity.age` (`~/.config` when unset) or the path `COOKWRIGHT_AGE_IDENTITY` names, never inside any git work tree, judged by the realpath of its directory (disposition 51): `secrets init` refuses such a path and doctor FAILs it.
7. Rule 3: doctor never prompts. `1password`: the template is parsed. `keychain`: items are found by attributes (`find-generic-password -s -a`, no `-w`), `present by name`; whether that lookup can raise the unlock dialog on a locked keychain is measured in QA (`lock-keychain` on the throwaway keychain) and the row is SKIP with the reason if it can (the wording "not measured" on a PASS line is superseded by disposition 45). `age`: the three files exist and are tracked; the identity's header (`age-encryption.org/v1`) decides `passphrase-protected`, else WARN naming the upgrade; the note never interpolates the line (a hand-made identity's first line is the key); the names are not the row's claim (disposition 45); nothing is decrypted.
8. Rule 9: no dependency. Echo-off input is `setRawMode` on a terminal stdin; no pseudo-terminal for the child.
9. Rule 4: backends behind one interface in `src/lib/secrets/backends/`, reaching their tools only through two new probes: `capture(cmd, args, { input, cwd, env, cap })`, synchronous (`runBounded` with `input`; budget-bounded inside doctor, capped at 120 s outside, and uncapped when the call prompts on a terminal: `age` with a passphrase-protected identity, `age -p`), and `spawnChild(cmd, args, opts)`, asynchronous (`spawn`, never `shell: true`), for the one child and for a tool's own prompt. Every helper runs with the scrubbed environment (disposition 50). The engine is tested with a fake backend and fake probes; each tool once for real (§8).
10. Rule 7 (never on a command line), deviating from the kickoff's keychain sentence and said so: `secrets set <target> <NAME>` on `keychain` never puts the value in an argument (the mechanism is disposition 60, provisional). For `age`, `secrets set` reads the value from a terminal prompt with echo off; `--stdin` reads one line from standard input instead (the fixture's path; a flag, so an agent's `echo | secrets set` is a visible choice). Without a terminal and without `--stdin`, `set` refuses. Never from an argument. `secrets init` (`age` only) prints what it will write and asks for consent, pipes the generated key through `age -p -o <identity>` (binary, not armored, so the header check of disposition 7 holds; age prompts), captures age's stderr and treats its `autogenerated passphrase` line as a failed init (file removed, refused: an empty passphrase is refused); `--no-passphrase` writes the key as generated, mode 600, the WARN state the guide names as weaker.
11. Rule 6: E-015 closes here. `secrets.carriers` reads `.envrc` tracked or at the root, any declared or ambient name (disposition 29) present in doctor's own environment, and an `export NAME=` or `NAME=` line (comments skipped) for such a name in `~/.zshenv`, `~/.zshrc`, `~/.zprofile`, `~/.bashrc`, `~/.bash_profile`, `~/.profile` (names and file names only; bounded reads under `home`). Guards `repo.config` (no names without one) and `repo.workTree` (the `ls-files` part) itself. With no `secrets` key the row still checks `.envrc`.
12. Rule 3: the keychain backend's real test uses a throwaway keychain (`create-keychain -p`, `unlock-keychain -p`, `set-keychain-settings` with no auto-lock, in a scratch directory; `delete-keychain` in `afterAll`; a vitest timeout) through an optional `keychain` argument that the product never passes; the test adds its items with `-w <value> <keychain>` (a throwaway value in a throwaway keychain, test-only) and exercises `resolve` and `inspect`; `set`'s path is measured in s3 and QA (disposition 60). `npm test` never touches a login keychain; the macOS CI job runs the real `security`.
13. Rule 3: `run`'s exit is the child's: its status; `128 + signal number` when a signal ended it; 127 when the command could not be spawned (naming it); 125 for every refusal before spawn (disposition 47). Signals per disposition 66; the pipes per disposition 59. The banner goes to stderr so a child's stdout stays a clean stream. The child's working directory is `process.cwd()`, not the config root.
14. Rule 2 and rule 3: the child's environment is the inherited environment with every declared name of every target, every ambient name (disposition 29), every backend control name (disposition 50), and any variable whose value equals a resolved value removed, then the target's values added; each removed name is on the banner as `dropped from the environment: NAME`. cookwright's own `process.env` is left as inherited; the values live in one `Map` until the child is spawned.
15. Rule 3: a 1Password template line is `NAME=op://<vault>/<item>/<field>` or `NAME=op://<vault>/<item>/<section>/<field>` with each segment `[A-Za-z0-9 ._-]+` (so no `$`, `{` or `}`, which `op inject` would expand from the environment), a blank line, or a `#` comment that does not itself look like `NAME=…`; any other line is a literal: doctor FAILs naming the line number, `run` refuses naming it, neither prints the line. `op inject -f -i <tpl>` runs with the scrubbed environment. The resolved output is parsed against the template's references (disposition 53).
16. Rule 5: the 3→4 migration changes nothing but the version: outcome `secretsNone` (`no secrets backend declared, Level 2 off (the secrets guide shows the key)`) when the key is absent, `secretsKept` when a `secrets` key is already present; `freshConfig` writes no `secrets` key.
17. Rule 3: `secrets.backend` reads PASS `no backend (Level 2 off)` when `secrets` is absent and `secrets.targets` PASS `no targets declared`, both measured facts, so the three rows are static (22 rows on this repo).
18. Rule 3 and rule 4: proof kinds are a registry: core `host` in `src/lib/secrets/proofs.mjs` plus `proofs` from each declared pack's manifest (`packs/supabase/pack.mjs` gains `proofs: { supabase: { names, prove } }`, data and pure functions importing nothing). The config validates `proof.kind` against `host` and the declared packs' kinds, one home, as it validates pack rules; an unknown kind is an invalid config naming the pack that has it. The JSON schema is structural (it cannot see the declared packs) and the guide says so.
19. Rule 3: the `supabase` kind is the origin's anchored check, lifted, with the kickoff's `<role>.<ref>`: a project URL is `https://<ref>.supabase.co`; a database URL names the ref as the pooler username `<role>.<ref>` (`^[a-z_][a-z0-9_]*\.<ref>$`) on a host ending in `.pooler.supabase.com`, or as the direct host `db.<ref>.supabase.co`; when both a `<role>.<x>` username and a `db.<y>.supabase.co` host are present, `x` and `y` must both be the ref; the userinfo is split at the last `@`, never by `new URL`; a value of neither shape is a mismatch; a connection parameter in the query string is a mismatch (disposition 65). The `host` kind compares `new URL(value).host` with the declared `host` canonicalised the same way (`new URL('https://' + host).host`: default port dropped, IPv6 bracketed, IDN punycoded; a `host` that does not round-trip is invalid), lower-cased, trailing dot dropped. A `ref` is `^[a-z]{20}$` in the schema.
20. Rule 7: nothing in the stage prints a value: tests assert on length or sha256; the fixture's synthetic values live in the script's memory and are asserted by length through the child; the closeout records the 1Password run's banner only.
21. Rule 7: before spawning, `run` checks every argument after `--` for a needle as a substring (the value and its encoded form); a match refuses naming the name and the argument's position (`argument 2 holds the value of DB_URL; read it from the environment inside the command instead`).
