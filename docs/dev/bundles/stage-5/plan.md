# Stage 5 — Secrets: one child process, target proof, never a plaintext file (E-015)

Written 2026-10-27 from `docs/dev/stage-5-kickoff.md` (decisions of 2026-10-26 taken as given). Revised the same day after two adversarial reads (security: 2 P1, 8 P2, 15 P3; codebase fit: 1 P1, 9 P2, 13 P3): dispositions 22 to 41 below, the P3s folded where a sentence does it, the rest in §11. Approved by the developer on 2026-10-27 with five P2 amendments and the two answers to §12 (dispositions 42 to 48), the five-session split accepted.

## 1. Context

The charter's Secrets decision: never a plaintext env file, not even as a fallback; a secret is injected into one child process with target proof; three backends at launch (1Password `op`, macOS Keychain, `age` with a passphrase-protected identity as the free universal path); no backend configured means Level 2 is off. The origin repo proved the contract over three bundles after two incidents (a stale export aimed a dev run at production; a process listing printed a password into a transcript). Stage 5 lifts the mechanism into the package: one command, proofs as data and pure functions, backends behind one interface.

What exists (*measured* in this planning session, 2026-10-27):

- The config is at version 3; `KNOWN_KEYS.top` in `src/lib/config.mjs` refuses unknown keys, so `secrets` needs version 4. `ci` is the model for an optional object with no default. The loader imports the pack registry (`KNOWN_PACKS`, `PACKS`) and already validates `packs[].rules` against each manifest, so it can validate a proof kind the same way. Migrations are pure steps in `src/lib/migrations.mjs` (imports nothing); outcome texts in `messages.migrate.outcomes`. `config.test.mjs` ties the schema's property names to `KNOWN_KEYS.*` and `version.enum` to `[CONFIG_VERSION, …MIGRATIONS keys]`; `src/migrate.test.mjs` holds thirteen literal `version 3` assertions and `scripts/ci/fixture.sh` two (`c.version === 3`, `already at version 3`).
- `LEVELS` in `src/lib/levels.mjs` holds only level 0 (15 required rows); `secrets.env` is not required by it. Level 2 exists only in docs. Kickoff decision 1 keeps it that way: the `secrets.*` rows are orthogonal, like pack rows.
- Doctor's rows are the static table `CHECKS` in `src/lib/doctor/registry.mjs` (19 rows) plus per-pack rows; a check is synchronous, `(repo, probes) → { status, note }`; a throw is a FAIL line, a `TimedOut` a SKIP; `runOne` SKIPs on the `config`/`git` flags only, so a check reads `repo.config` and `repo.workTree` itself. A bump touches `block.test.mjs`, `test-helpers.mjs` (`v2Block`/`v1Block` derive from a v3 render), `init.test.mjs`, `doctor.test.mjs` (`refreshed(3)`, stale cases) and this repo's `AGENTS.md` (`rules.block` FAILs until `init` reruns). The pack manifest has no key whitelist: `proofs` and `ambient` are accepted as data (they must not look like a rule).

- On this machine: `op` 2.39.0, `age` 1.3.2, `age-keygen`, `security`, `gitleaks`, `supabase` on PATH; macOS 26.6.2; Node 20.19.4.

- The origin's anchored proof: project URL host `<ref>.supabase.co`; database URL username `<role>.<ref>` on the pooler or host `db.<ref>.supabase.co` direct; userinfo split at the *last* `@`, password after the first `:`; a ref in the password, path, query or database name is a mismatch (its suite's `unanchored(ref)` builds those three); its read-only variant also requires a `*pooler*` host for the username anchor. Its recipients-file guard (`ops__require_committed_recipients`): tracked, byte-identical to HEAD, fingerprints printed. Its redaction is a whole-URL `sed` over a pipe; its stated residual: the injecting process's environment block holds the values for the run.

## 2. Decisions

Taken by the developer on 2026-10-26 (kickoff): secrets sit beside the levels (the `secrets.*` rows are orthogonal; Level 2's requirement list claims them when Level 2 opens); the `age` ciphertext and recipients are tracked, the identity alone is the secret; a target without a proof is WARN in doctor and `unproved` on the banner.

Dispositions by the Judgment rules, to be recorded with `bundle decide` at kickoff:

1. Rule 3 (claim what was measured): `run` splits its argv at the first `--` before `parseArgv`; everything after it is the child's, verbatim, flags included. No `--`, or nothing after it, is the usage, exit 2. A target name is `^[a-z][a-z0-9-]*$`, a secret name `^[A-Z][A-Z0-9_]*$`, both validated by the config.
2. Rule 3 and rule 7: a proof names the names it covers, never infers them by value shape (a Sentry DSN beside a Supabase URL is a declared name with no proof, and the banner says so). `{ kind: 'supabase', ref, names? }` defaults `names` to those of `SUPABASE_URL` and `DB_URL` the target declares (invalid when neither); `{ kind: 'host', host, names }` requires `names`. Each covered name must be in the target's `names`; a covered value that does not satisfy the kind is a mismatch, never skipped; a proof covering zero names is invalid.
3. Rule 2 (a chosen state is WARN): a target without `proof` is `secrets.targets` WARN naming it and `unproved` on the banner; a declared proof that fails refuses the run with the kind's reason (the name, the expected identifier, the anchor that failed; a found ref only when the value parsed as a `*.supabase.co` URL, else `not a supabase.co URL`; never a value, host or password).
4. Rule 1 governs hooks; `run` is the user's own command and refusing is the product: a missing backend tool, a wrong platform, a missing name, a literal in a template, a failed proof, a malformed resolved line, a value on the child's command line (dispositions 21, 22) each print one line naming the fix, exit 125, nothing spawned (disposition 47). The hooks are unchanged.
5. Rule 3: the redaction guarantee costs the child its output terminal, said rather than weakened. The child gets stdin inherited (a prompt that reads the terminal still works; `age` and `security` open the tty themselves), stdout and stderr as pipes through the redactor, so it sees no TTY on its outputs: no colour unless forced, no pager. The banner says so once. Redacted: every injected value, its `encodeURIComponent` form, and, for a value that parses as a URL with a password of at least 8 characters, that password alone, decoded and encoded, each replaced by `<NAME>`. The guide says these are the forms covered (a base64, JSON-escaped or shell-quoted value is not).
6. Rule 5 and rule 7: `secrets/` is a fixed directory at the config root (`secrets/<target>.env.tpl`, `secrets/<target>.env.age`, `secrets/recipients.txt`); the ciphertext is armored (`age -a`): text, diffable, through the pre-commit scan like any file (the fixture commits one). The identity lives at `$XDG_CONFIG_HOME/cookwright/identity.age` (`~/.config` when unset) or the path `COOKWRIGHT_AGE_IDENTITY` names, never under the work tree, judged by `realpath` of its directory against the work tree's (a symlinked `~/.config` into a dotfiles repo counts): `secrets init` refuses such a path and doctor FAILs it.
7. Rule 3: doctor never prompts. `1password`: the template is parsed; sign-in reads `not measured`. `keychain`: items are found by attributes (`find-generic-password -s -a`, no `-w`), `present by name`; whether that lookup can raise the unlock dialog on a locked keychain is measured in QA (`lock-keychain` on the throwaway keychain) and the row reads `not measured` if it can. `age`: the three files exist and are tracked; the identity's header (`age-encryption.org/v1`) decides `passphrase-protected`, else WARN naming the upgrade; the note never interpolates the line (a hand-made identity's first line is the key); the names are not the row's claim (disposition 45); nothing is decrypted.
8. Rule 9: no dependency. Echo-off input is `setRawMode` on a terminal stdin; no pseudo-terminal for the child.
9. Rule 4: backends behind one interface in `src/lib/secrets/backends/`, reaching their tools only through two new probes: `capture(cmd, args, { input, cwd, env, cap })`, synchronous (`runBounded` with `input`; budget-bounded inside doctor, capped at 120 s outside, and uncapped when the call prompts on a terminal: `age` with a passphrase-protected identity, `age -p`), and `spawnChild(cmd, args, opts)`, asynchronous (`spawn`, never `shell: true`), for the one child and for `security`'s own prompt. The engine is tested with a fake backend and fake probes; each tool once for real (§8).
10. Rule 7 (never on a command line), deviating from the kickoff's keychain sentence and said so: `security add-generic-password` takes the value only as an argument or through its own prompt, so `secrets set <target> <NAME>` on `keychain` runs it with `-w` last and the terminal inherited; the value never reaches cookwright. For `age`, `secrets set` reads the value from a terminal prompt with echo off; `--stdin` reads one line from standard input instead (the fixture's path; a flag, so an agent's `echo | secrets set` is a visible choice). Without a terminal and without `--stdin`, `set` refuses. Never from an argument. `secrets init` (`age` only) prints what it will write and asks for consent, pipes the generated key through `age -p -o <identity>` (binary, not armored, so the header check of disposition 7 holds; age prompts), captures age's stderr and treats its `autogenerated passphrase` line as a failed init (file removed, refused: an empty passphrase is refused); `--no-passphrase` writes the key as generated, mode 600, the WARN state the guide names as weaker.
11. Rule 6: E-015 closes here. `secrets.carriers` reads `.envrc` tracked or at the root, any declared or ambient name (disposition 29) present in doctor's own environment, and an `export NAME=` or `NAME=` line (comments skipped) for such a name in `~/.zshenv`, `~/.zshrc`, `~/.zprofile`, `~/.bashrc`, `~/.bash_profile`, `~/.profile` (names and file names only; bounded reads under `home`). Guards `repo.config` (no names without one) and `repo.workTree` (the `ls-files` part) itself. With no `secrets` key the row still checks `.envrc`.
12. Rule 3: the keychain backend's real test uses a throwaway keychain (`create-keychain -p`, `unlock-keychain -p`, `set-keychain-settings` with no auto-lock, in a scratch directory; `delete-keychain` in `afterAll`; a vitest timeout) through an optional `keychain` argument that the product never passes; the test adds its items with `-w <value> <keychain>` (a throwaway value in a throwaway keychain, test-only) and exercises `resolve` and `inspect`; `set`'s prompted path is the developer's QA. `npm test` never touches a login keychain; the macOS CI job runs the real `security`.
13. Rule 3: `run`'s exit is the child's: its status; `128 + signal number` when a signal ended it; 127 when the command could not be spawned (naming it); 125 for every refusal before spawn (disposition 47). cookwright ignores SIGINT and SIGTERM while the child runs (the terminal delivers them to the child), waits for the child, sets `process.exitCode` and lets the event loop drain (never `process.exit`, which truncates a piped stdout); after the child's `exit` the pipes are drained for at most 200 ms, then `end()`: a grandchild that keeps the pipe open past that writes unseen. The banner goes to stderr so a child's stdout stays a clean stream. The child's working directory is `process.cwd()`, not the config root.
14. Rule 2 and rule 3: the child's environment is the inherited environment with every declared name of every target and every ambient name (disposition 29) removed, and any variable whose value equals a resolved value removed, then the target's values added; each removed name is on the banner as `dropped from the environment: NAME`. cookwright's own `process.env` is left as inherited; the values live in one `Map` until the child is spawned.
15. Rule 3: a 1Password template line is `NAME=op://<vault>/<item>/<field>` or `NAME=op://<vault>/<item>/<section>/<field>` with each segment `[A-Za-z0-9 ._-]+` (so no `$`, `{` or `}`, which `op inject` would expand from the environment), a blank line, or a `#` comment that does not itself look like `NAME=…`; any other line is a literal: doctor FAILs naming the line number, `run` refuses naming it, neither prints the line. `op inject -f -i <tpl>` runs with the scrubbed environment. The resolved output is parsed as `NAME=value` at the first `=`, no trimming; a value may hold any byte but a newline (a malformed line is refused by number only; multi-line values are backlog); an empty value is `missing`.
16. Rule 5: the 3→4 migration changes nothing but the version (outcome `secretsNone`: `no secrets backend declared, Level 2 off (the secrets guide shows the key)`); `freshConfig` writes no `secrets` key.
17. Rule 3: `secrets.backend` reads PASS `no backend (Level 2 off)` when `secrets` is absent and `secrets.targets` PASS `no targets declared`, both measured facts, so the three rows are static (22 rows on this repo).
18. Rule 3 and rule 4: proof kinds are a registry: core `host` in `src/lib/secrets/proofs.mjs` plus `proofs` from each declared pack's manifest (`packs/supabase/pack.mjs` gains `proofs: { supabase: { names, prove } }`, data and pure functions importing nothing). The config validates `proof.kind` against `host` and the declared packs' kinds, one home, as it validates pack rules; an unknown kind is an invalid config naming the pack that has it.
19. Rule 3: the `supabase` kind is the origin's anchored check, lifted, with the kickoff's `<role>.<ref>`: a project URL is `https://<ref>.supabase.co`; a database URL names the ref as the pooler username `<role>.<ref>` (`^[a-z_][a-z0-9_]*\.<ref>$`) on a host ending in `.pooler.supabase.com`, or as the direct host `db.<ref>.supabase.co`; when both a `<role>.<x>` username and a `db.<y>.supabase.co` host are present, `x` and `y` must both be the ref; the userinfo is split at the last `@`, never by `new URL`; a value of neither shape is a mismatch. The `host` kind compares `new URL(value).host` with the declared `host` canonicalised the same way (`new URL('https://' + host).host`: default port dropped, IPv6 bracketed, IDN punycoded; a `host` that does not round-trip is invalid), lower-cased, trailing dot dropped. A `ref` is `^[a-z]{20}$` in the schema.
20. Rule 7: nothing in the stage prints a value: tests assert on length or sha256; the fixture's synthetic values live in the script's memory and are asserted by length through the child; the closeout records the 1Password run's banner only.
21. Rule 7: before spawning, `run` checks every argument after `--` for a needle as a substring (the value and its encoded form); a match refuses naming the name and the argument's position (`argument 2 holds the value of DB_URL; read it from the environment inside the command instead`).

## 3. Scope

In: the kickoff's eight items with the dispositions above. Out (kickoff): the Supabase ops pack (E-001) and the OTA preflight; a Linux secret-service or Windows Credential Manager backend; the re-exec that would scrub the injecting process's own environment; a gate check that needs a credential; B-018; any change to the hooks. ## 4. Design

### 4.1 Config version 4

### 4.2 The engine: `npx cookwright run <target> -- <command…>`

`src/run.mjs` and `src/lib/secrets/engine.mjs` (steps, each under 40 lines; `Refused` for product refusals, disposition 34):

1. `splitArgv(argv)` → `{ own, child }` at the first `--` (`src/lib/cli.mjs`); one positional; `onlyFlags(flags, [])`.
2. `openConfig`; refuse when `secrets` is absent, the target unknown (naming the declared ones), the backend's tool missing (`needs <tool>: <install line>`) or platform wrong.
3. `backend.resolve(target, ctx)` → `Map<name, value>` (§4.3); a declared name the backend lacks, or empty, refuses naming it and the `secrets set` line (or the template for 1Password).
4. `prove(values, target.proof, proofKinds(config))` → `{ ok, proved, against, kind, reason }` (§4.4); `ok: false` refuses; no proof → `proved: []`.
5. `childEnv(env, dropNames, values)` → `{ env, dropped, inheritedValues }` (dispositions 14, 29); then `argvCheck(child, needles(values, inheritedValues))` (dispositions 21, 22).
6. Banner on stderr (`messages.run.banner`): `run: <target> · injected A, B, C · proved A, B against <ref> (supabase) · unproved C · dropped from the environment: B, SUPABASE_DB_URL · child output piped through the redactor (no terminal on stdout/stderr)`; parts absent when empty; the keychain service when that backend is in use.
7. `probes.spawnChild(cmd, args, { env, cwd: process.cwd(), stdio: ['inherit', 'pipe', 'pipe'] })`; each pipe through a `Redactor` to the matching process stream; signals, drain and exit per disposition 13.

`main(argv, { cwd, env, home, probes, backends })` returns the exit code; tests call it in process with a fake backend, a fake `spawnChild` (a `node -e` child printing the lengths of named variables, or echoing a value to prove redaction) and a fake `capture`.

### 4.3 The backends

- `src/lib/secrets/envfile.mjs`: `parseEnv(text)`, `replaceLine(text, name, value)`, pure; `src/lib/secrets/recipients.mjs`: `parseRecipients`, `requireCommittedRecipients` (through `gitRun` from `doctor/repo.mjs`).

`src/secrets.mjs`: `secrets init [--no-passphrase] [--yes]`, `secrets set <target> <NAME> [--stdin]`; `src/lib/secrets/prompt.mjs` `readValue({ stdin, tty, flag })` (disposition 10); the command prints `secrets: set NAME for <target> (<backend>[, service <svc>])`, never a value or its length.
