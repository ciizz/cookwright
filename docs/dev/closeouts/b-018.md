## What B-018 was

After `npx cookwright init` on an Expo app, the user's own lint run failed: `npx expo lint` (the scaffold's `npm run lint`, the editor's view) linted the two workflow pointers init writes under `.claude/workflows/`, symbolic links to the package's workflow scripts, whose format has a top-level `return` ESLint cannot parse, and reported `Parsing error: 'return' outside of function` for each. Found by stage 4's QA (b) on a fresh scaffold with cookwright 0.2.0 from npm, the release that carries the defect. The pack exports' ignores were per block (each block also sets `files` and `rules`), so they kept the pack's rules off those paths and left the user's own config linting them; the hook and the ratchet were never affected, since they skip links and lint blobs.

## What shipped

Each pack's ESLint export now starts with one rules-less block, `{ name: 'cookwright/<pack>/ignores', ignores: ['.claude/workflows/**'] }`, a global ignore in flat config wherever the spread lands. The glob is as narrow as the plan review made it: `.claude/workflows/` is the one place init writes a file ESLint lints and the one format ESLint cannot parse, so a user's own workflow script there is ignored for the same reason, and nothing else of the host directories is: `.claude/hooks/*.ts` and a user's own skills' scripts stay linted by their own config, the skill pointers are directories of Markdown, `.codex/` holds `hooks.json`. The per-block `IGNORES` keep their bytes. The engine needed no change: `coverage()` already drops a block without `rules` before `wiring()`, `scopeAt()` and `changedAt()` read it. The export's test finds the strings and client blocks by name instead of position, treats a rules-less block as covering nothing, and asserts the new block's shape and reach (the pointer paths matched, `.claude/hooks/x.ts`, `.claude/skills/mine/index.ts`, `.agents/skills/mine/index.ts` and `.codex/hooks.json` not); the engine test asserts `coverage()` over the real export equals the export minus its first block. The fixture gained a `lint_run` step after doctor: `npx eslint . --format json` under `set -euo pipefail` with the exit captured, 0 or 1 accepted, 2 or more failing with ESLint's stderr tail, then the report read for no file under `.claude/` and `App.tsx` reported under `i18next/no-literal-string`, each failure with its own text, an unreadable report included (review:fix's one P3). The standards guide says what a user's own lint run shows: every violation at error severity, legacy ones included, the hook and the gate judging only the change, and the workflow directory ignored.
